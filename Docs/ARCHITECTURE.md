# Architecture

The [ability resolution plan and implementation record](plans/COMBAT_RESOLUTION_PLAN.md) documents the shared player/enemy executor, approved rule alignment and explicit room scaling.

The [combat reaction architecture plan and implementation record](plans/COMBAT_REACTIONS_PLAN.md) documents typed damage origins, synchronous reaction continuations and the approved immediate cancellation after actor knockout.

`src/game/` owns content, commands, battle rules, seeded RNG, and save validation. It imports only its own modules, Immer, and Zod. It does not access the DOM, React, filesystem, Steam, clocks, or ambient randomness. `scripts/checks/boundaries.mjs` parses source and checks resolved import paths and ambient capability references; CI also runs Knip for unused files, exports and dependencies.

`dispatch(state, command)` returns either an accepted immutable state with ordered presentation events or a rejection retaining the original state. Validation occurs before RNG consumption or mutation. Gameplay and progression settle synchronously. Animation is a consumer of results; it cannot pay mana, damage a creature, grant a reward, or unlock content.

`src/application/session.ts` owns the runtime store and serialized save queue. Commands admit the encoded save to the serialized queue before publishing committed state, so synchronous subscribers cannot reorder saves or dispose before an accepted save is admitted. Startup keeps commands unavailable until local loading and bounded cloud reconciliation finish. Load examines primary followed by backups; malformed saves never enter gameplay. All-invalid development candidates silently fall back to a fresh profile; read I/O failures allow in-memory play after an automatic retry or bounded wait. Failed writes retain the live game and retry the latest state in the background. Disposal revokes commands and unsubscribes the close handshake while draining admitted writes.

`src/platform/` defines storage, desktop quit, and optional Steam cloud/achievement capabilities. The browser uses localStorage; desktop uses a sandboxed preload IPC bridge. Steam is optional. Desktop adapters expose display preferences, account-scoped cloud transport and overlay state; gameplay never requires Steam. Cloud reconciliation belongs to the application and native calls run in an owned utility process.

`src/ui/` consumes the session and owns transient targeting, inspection, menu, and input modality. Zustand subscriptions expose application state. Motion respects the user's reduced-motion preference. Standard gamepads and keyboard navigation feed semantic actions and share focus navigation.

## Repository organization

The runtime keeps its layer boundaries: gameplay in `src/game/`, command and save orchestration in `src/application/`, capability adapters in `src/platform/`, presentation in `src/ui/`, and privileged Electron code in `desktop/`. [Architecture checks](../scripts/checks/boundaries.mjs) enforce import direction, including keeping development harnesses outside runtime dependencies.

Within presentation, `battle/`, `expedition/`, `collection/`, `talents/`, `settings/`, `inspection/` and `menu/` own their features and styles. `menu/` contains the home screen, Glossary and shared home/pause actions; the expedition owns unlock and owned-Boon content. `audio/` owns playback; `shared/` owns reusable artwork, layout, focus and input. [App](../src/ui/App.tsx) composes screens and remains the single owner of transient navigation, input routing, command callbacks and modal focus restoration. Extracted content receives data and callbacks; it does not create competing route or modal owners. [Inspection requests](../src/ui/shared/inspection-model.ts) and [input controls](../src/ui/shared/input.ts) are owned independently of screen implementations. Registered upstream primitives remain in `src/components/ui/`. React surface measurement and modal lifecycle hooks live in `src/ui/infrastructure/`, below primitives and feature compositions. `src/lib/` contains dependency-light utilities without React, feature, application, platform or gameplay imports. Architecture checks also prevent primitives and presentation infrastructure from importing those higher-level owners.

Shared card presentation, combat status badges, value labels and Health/Block readouts live in `src/ui/shared/`. The shared inspection request contract lives in `src/ui/shared/inspection-model.ts`, so reusable deck and roster views do not depend on the inspection feature. Shared presentation may consume gameplay queries and infrastructure, but cannot import UI feature folders. Battle targeting and forecasts remain in `src/ui/battle/` and compose those shared readouts. Component moves retain existing stylesheet declaration order; shared status and readout selectors currently remain in the ordered battle stylesheet to preserve the cascade.

`src/ui/styles.css` is the ordered stylesheet entrypoint: it imports tokens, the shared primitive skin, shared artwork/layout/keyword styles and each feature stylesheet. Keep feature layout in its feature folder, reusable artwork and composition in `src/ui/shared/`, and primitive states in `src/ui/design-system.css`. When moving rules, retain repeated-selector order and review interactions between shared and feature selectors; unchanged declarations alone do not establish unchanged rendering.

Authored [species](../src/game/content/species.ts), [cards](../src/game/content/cards.ts), [talents](../src/game/content/talents.ts), [Boons](../src/game/content/boons.ts) and [encounter templates](../src/game/content/encounters.ts) live in `src/game/content/`, with shared definition types beside them. `content.ts` retains the catalog lookup API, [card rules](../src/game/card-rules.ts) own effect descriptions and enemy adaptation, and `progression.ts` owns progression calculations. Catalog array order is intentional: preserve it when reorganizing definitions because seeded offers and selection consume it.

Gameplay helpers sit below the command engine: [seeded randomness](../src/game/random.ts) owns rolls and shuffles; [card zones](../src/game/card-zones.ts) own the seven-card hand limit, buffer promotion and ordinary/keyword draws; [progression](../src/game/progression.ts) owns starter count. Save validation, commands and presentation consume these canonical owners directly. Extracting these helpers must preserve RNG consumption, zone order and committed event order.

`src/tooling/` owns playthrough, balance and performance harnesses. These consume runtime contracts; runtime code cannot import them. Auto-play's shared battle policy remains in `src/application/battle-policy.ts` because the player application uses it.

`tests/unit/` groups focused suites by owner: `game/`, `application/`, `platform/`, `ui/`, `tooling/` and `simulation/`. `tests/integration/` retains cross-layer creature, gameplay and recovery scenarios, including gameplay-to-feedback, Auto-play, save/resume and rendered recovery contracts. Both groups use the same Vitest runner; the Node/DOM environment remains a property of each suite. Shared scenario builders live in [tests/support/game.ts](../tests/support/game.ts), available to unit and browser suites. `tests/e2e/` retains rendered integration journeys. [Verification policy](../CONTRIBUTING.md#verification) and the fixed local smoke selection are unchanged.

[Scripts](../scripts/README.md) are grouped by workflow. npm command names remain the public interface; worktree creation, cleanup and integration retain their root script entrypoints. Configuration, documentation, source-policy checks and owner lookup must follow file moves together.

The [renderer config](../tsconfig.json) supplies DOM and Vite globals; [Node tooling and configuration](../tsconfig.node.json) supplies Node globals; [tests and design studies](../tsconfig.test.json) supplies both DOM and Node capabilities. ## Domain identity

Species and card definitions use stable authored IDs. A run-specific creature owns three card instances, each carrying its effect level. Creature IDs persist across deployment and backup moves. Free manual combat swaps retain card-instance slot IDs and zone positions while replacing definitions and owners; swap cards instead remove outgoing slots from all zones and shuffle the incoming kit into the draw pile before subsequent draws; definition IDs and instance IDs are deliberately independent. The remembered starting lineup stores creature IDs separately from the currently deployed team. Multiple copies of a species are supported; swaps, release choices, card ownership and battle hover/focus details address an individual by its ID. The roster species list counts copies rather than enforcing species uniqueness. No individual creature carries progress between runs.

The authoritative aggregate includes permanent species unlocks, win count, keyword XP, talent IDs, and currency; plus the current roster, backup creature state, starting lineup, deployed team/cards, run-wide boons, encounter, phase, and battle. Battle rewards are saved receipts. Banking happens atomically at battle settlement; choosing or skipping a reward never banks them again. Battle tracks draw, hand, hidden overflow buffer, discard, health/block, enemy targets, turn, and mana. Knockout leaves inert card slots in battle zones. Normal draws skip them and the UI never renders them for knocked-out owners. If all deployed creatures fall, the next draw reserves slots for healthy replacements, allowing recovery without bonus cards. Enemy attacks stop when no deployed target lives; defeat requires all roster members to fall.

A linear-congruential RNG is explicit state. Destination offers, shuffles and intent choices consume it; presentation does not. Equal initial seeds and accepted command sequences yield equal results. Rejected commands retain state and RNG.

## Save contract

Development saves are disposable: there are no released player saves to preserve. Do not implement migrations or backward compatibility unless explicitly requested. Obsolete formats are rejected; loading falls back to valid current-format backups or a fresh profile silently. The canonical agent policy is in [AGENTS.md](../AGENTS.md#development-saves).

The current save version is owned by [save-format.json](../src/game/save-format.json), shared by gameplay validation and desktop storage, and included in the packaged application. The current format is validated by Zod and semantic checks for content IDs, ownership, unique card zones, health bounds, lineup completeness, saved encounter packs, and phase/outcome coherence. Only the current format is supported in browser and desktop storage; fixtures track that format. Valid current-format backups remain recoverable.

Battle settlement banks actual retained currency and keyword XP once. Ordinary fights offer recruitment only; intermediate bosses offer up to three unowned Boons only. The shared Victory screen consumes committed receipts, requires recruitment when offered, and accepts a Boon choice or Skip for boss rewards, with no acknowledgement phase or Continue command. An empty eligible pool advances immediately; final victory and defeat go directly to Journey results. The journey summary retains the outcome, battle count, gains, new unlocks, and last-battle receipt; opening results never grants rewards or saves.

Hands contain at most seven cards. Extra draws enter a FIFO buffer, which cannot be played or inspected as a separate zone. Accepted plays refill newly open hand slots from that queue without RNG. End turn discards the visible hand, retains overflow, restores the next player turn’s maximum Mana (four before talent modifiers) and draws four cards after promoting waiting cards. Free manual swaps preserve buffered card slots and update their owner along with other zones. Save validation includes the buffer in zone uniqueness/completeness and rejects a waiting buffer alongside an unfilled hand.

Browser saves rotate application-validated recoverable checkpoints into backup1 and backup2 before installing the next snapshot. The application supplies the current-format validation predicate with each write; the storage adapter imports no gameplay implementation and preserves existing backups when no validation policy is supplied. Desktop serializes writes, flushes a temporary file, rotates backups, then renames it over the primary. A partial backup rotation still leaves the old primary intact. Atomic rename guarantees depend on filesystem behavior; sudden power loss is not equivalent to graceful quit.

Desktop window close and application quit request a renderer flush first. The session pauses new commands, finishes its queue, and retries the latest state once if saving failed before acknowledging close. Main then revokes IPC admission, drains admitted writes, and quits. A persistent save failure is recorded internally and does not prevent closing. Renderer crashes and OS force-kill cannot run this handshake.

## Command resolution and previews

With Auto-end turn enabled (the default), spending the final Mana resolves the enemy turn inside the same command and revision. The play command records its effective preference. Disabling it retains a saveable and resumable player turn at zero Mana; normal victory/defeat settlement remains immediate. Preview resolution is independent of this setting. Victory takes precedence over automatic turn advancement. Card previews run the same card-effect resolution without settling battle rewards, advancing the enemy turn, or publishing/saving the preview state. This retains the final enemy health forecast even when committing the card will advance directly to destinations.

## Keyword foundation

`src/game/keywords.ts` owns keyword vocabulary, definitions, aliases, availability, damage identities, and authored-effect classification. Content, progression and glossary consume it. The catalog describes active Alchemy-derived damage, defenses, statuses and removal mechanics. Gold stays outside the keyword catalog; Wish, Consume, Companion and Archery are excluded. Progression eligibility remains explicit and save-compatible. Presentation-only word matching cannot assign gameplay effects or XP. See [Keywords](KEYWORDS.md).

## Discovery and diagnostics

Permanent discovery stores encountered and recruited species separately from starter unlocks. Collection and later starter drafts use only recruited species. First-journey onboarding samples three offers from the authored eligible pool and starts with one chosen creature, collecting it on Begin journey. Later journeys save three rounds of three offers and require three picks. Accepted battle entry discovers the exact enemy group, and accepted recruitment increments its permanent copy count, capped at six. The first copy collects the species at zero stars; duplicates add one star each, up to five. The committed onboarding starter supplies one initial copy; later starter drafts grant no copies. Releasing journey creatures never removes permanent copies. Each species owns six passive tier slots in content. Authored tiers replace the full passive and can compose card bonuses, battle-start effects and reactive effects. All six tiers are required and must have distinct gameplay effects; catalog validation rejects missing tiers and repeated effect sets even when their wording or ordering differs. Combat, previews and inspection resolve the same player tier, while enemies retain base effects. Encounter and victory unlocks do not count as collection. Collection creature pages show the permanent active trait and all three base abilities directly, independently of journey card upgrades and battle modifiers. Collection is accessible through battle Pause and returns to unchanged combat. Collection browsing and out-of-battle inspection consume no RNG, grant no discovery and write no save. Loss, return home and new journeys retain knowledge. Save validation rejects duplicate or unknown discovery records, recruitment without an encounter, ineligible starter offers, incomplete offers and invalid selections. Starter offers persist across reloads and rejected commands preserve RNG. Enemy groups grow from one to two to three across the first three battles and stay at three thereafter, including bosses. No historical discovery is inferred for obsolete saves.

`src/application/diagnostics.ts` owns a bounded local collector exposed by the session. Its platform port owns persistence, separate from the game save. Entries contain selected revision/phase fields rather than arbitrary game objects. No player-facing report or clipboard export is exposed. Sink failures and recursive logging cannot affect commands or saves. Session disposal revokes collection. `committedCommand` is transient session presentation metadata and never enters the saved aggregate; loading a checkpoint does not manufacture a new committed action or replay audio.

## Combat and destination health

`src/game/abilities.ts` owns the single synchronous ability executor for player cards, previews and enemies. It resolves repeats, targets, primary effects, recipient extras and global extras within the engine's Immer transaction. Exhaustive switches require explicit execution and support decisions for new effect kinds. The engine retains command validation, Mana, card zones, accepted-play counters, XP, turn scheduling and final settlement. Application publication and saves remain outside gameplay.

`src/game/ability-values.ts` shares magnitude policy between execution and displayed rules. Both sides start with authored ability values and the same intrinsic passive calculation. Enemies store explicit room power (1 + room index / 10); ability damage, healing and Block scale once, including extras. Chances, effect counts, resource grants and passive tiers do not scale. Enemy Health uses the same depth curve. Save validation requires the exact power and Health for the saved encounter; obsolete development saves are rejected without migration.

`src/game/combat.ts` exposes shared combat entry points. [Combat policy](../src/game/combat-policy.ts) owns typed packet origins and reaction eligibility; [combat resolution](../src/game/combat-resolution.ts) owns synchronous, depth-first reaction continuations for damage, healing, protection, statuses, Leech and control. Generator frames yield typed child operations to a local stack; children finish before their parent resumes, without recursively entering mutation handlers. [Combat state helpers](../src/game/combat-state.ts) own atomic mutations and read-only queries. Armor removal records a transient, once-delivered depletion receipt at the positive-to-zero transition; later regrant and depletion produce a new receipt. No stack, receipt or continuation enters saves or published state. Retaliation knocking out the acting creature stops its remaining hits, extra effects and repeats; Death's Door at 1 Health allows continuation. Existing committed effects remain applied. Seeded Dodge and 5% base Critical chance retain their packet policies. Both sides use half maximum Health for Stun/Freeze. Player-only Death's Door, talents, Boons, card upgrades and collected passive ranks are explicit ownership exceptions. Enemies use base passive tiers and have no automatic round healing. The command resolver owns turn sequencing and final settlement; enemies knocked out by their start-of-turn status damage cannot act. Enemies select a supported species ability without immediately repeating the last choice. The exhaustive enemy adapter omits hand/Mana extras and excludes resource-only abilities; draw-plus-self-heal converts to its healing effect. Enemy target choices are AI policy, not a separate effect implementation. Selection happens at the action window, never during inspection, and next intentions remain hidden.

Health and knockouts persist through victories, rewards, lineup changes and destination entry. Battle setup resets combat effects without restoring Health. Campfire appears beside destination choices whenever any roster creature, including a backup or knockout, is missing at least 30% of maximum Health. Rest restores 30% maximum Health to the whole roster, capped at full Health, and returns to the same combat offers without advancing the encounter or changing RNG. It remains available while the threshold is met. Visiting enters a saved Campfire phase. Rest awards no Gold or XP. Eligibility and displayed recovery share the gameplay helpers in `src/game/support.ts`.

Draw and discard surfaces use blank portrait art and the existing modal owner. During battle, card rules remain on hover/focus without nested inspection. Pile viewers sort by definition and instance identity, never draw order. Browsing does not publish gameplay, consume RNG or save.

## Automated and development combat

The pure application battle policy scores only visible cards and creatures, using stable identity tie breaks and no gameplay RNG or hidden intentions. Headless heuristic runs and player Auto-play share it. The UI scheduler admits at most one command per 700 ms, pauses while obscured or unfocused, and cancels pending callbacks on manual takeover, completion, navigation home or disposal. It never makes reward or progression choices. Session disposal makes readiness unavailable before draining admitted saves.

Development victory uses an explicit session capability supplied only by development startup. Ordinary dispatch rejects it. It marks enemies defeated and reuses ordinary settlement, events and saving, preserving roster Health and banking actual earned XP. Packaged desktop startup ignores development URLs.

Unlock reveals observe newly committed species additions that appear in journey unlock receipts. Consumption is transient for the mounted session; loading completed saves and reopening results never manufacture another reveal.

Talent categories are consolidated independently of combat damage identities. The current format stores Boon IDs, first-Burn consumption, periodic status attribution, pending creature-owned talent rewards, remaining control windows, and already-banked talent Gold. Old development saves, including Forge state and relic fields, are rejected. No capability or local display preference is restored from progression.

## Support visits and spending

An optional Merchant is offered before encounters 2 and 6. It is visible and enterable only when at least one stocked item is affordable. These saved visits preserve combat offers and do not replace or advance battles. Merchant stock contains up to two unowned Boons at 20 Gold each, or 13 with Merchant's Favor when stock is prepared, with one purchase per visit. Gold is the existing permanent currency. Entering commits a visit; leaving consumes it, and beginning the next battle forfeits it. Inspection is read-only. Commands address visit/slot identities and validate before mutation; reload cannot refresh stock or repeat purchases. Merchant state remains valid during a Campfire visit.

Journey currency measures gross retained earnings, independently of the remaining wallet. Boss rewards contain up to three eligible unowned Boons and skip only an empty pool. Support state, stock, price bounds, receipts and phases are validated together in the current save format; obsolete development saves are rejected.

## Cloud reconciliation and device preferences

`src/application/cloud.ts` validates current gameplay payloads and hashed envelopes, compares causal ancestry, and owns automatic conflict resolution. It never merges progression fields. Each device writes two alternating remote slots; another device's slots are read-only. Unknown ancestry creates competing heads; prefer the intact local head, otherwise choose by stable snapshot ID, and preserve alternatives before recording all heads as ancestors. Replacements preserve competing snapshots locally before installation through the serialized save lane. Snapshot lineage is bounded to 64 ancestors and remote inventory to 32 device streams / 64 files, at most 1 MiB each. Invalid or oversized files pause upload; they are not deleted.

Local saves remain authoritative offline. Failed sync retries in the background without replacing the active journey, preserving remote alternatives before recording their ancestry. Cloud metadata is durably written after the local gameplay save and before upload; transport cannot hold the local save queue. Cloud and local failure states are internal diagnostics, never player-facing status. Startup reconciles before command admission and automatically continues locally after failure or a five-second wait. Late reads cannot replace a session after offline takeover. Shutdown drains admitted local writes and allows at most two seconds for uploads. A utility process contains blocking native transport and is terminated on owned app shutdown.

`desktop/steam.cjs` pins an optional Steam account, isolates its local profile from standalone progress, and automatically adopts valid standalone progress for a new Steam profile while preserving the original. `desktop/steam-config.json` holds Fauna's own App ID; its default null disables real Steam. Browser, smoke, preview and performance profiles never access live Steam. Account changes reject transport and require restart. Without a Steam client, ordinary launch continues the last locally used Steam profile with sync unavailable; isolated automation ignores that pointer. A newly identified account always selects its own directory, and the standalone original remains separate. Overlay activation synchronously revokes commands, cancels targeting/Auto-play and opens the existing pause menu; closing the overlay does not resume automatically.

`desktop/display.cjs` owns Windowed/Fullscreen and reachable window bounds, stored separately from progression and Cloud. Renderer settings use the typed authorized preload capability; automation has fixed isolated geometry. Native transitions and monitor removal never change artwork dimensions. After-pack fuses and browser snapshots are checked on the actual Windows artifact before the renderer-only packaged smoke; Node inspection is disabled.

Save loading tries intact current-format backups without announcing recovery. All-invalid development saves fall back to a fresh playable profile. Read access failure is retried once, then allows in-memory play; failed writes retry every five seconds with the newest committed state and stop on disposal. A write following read failure must first regain read access so unknown data is not blindly rotated. See the [silent recovery policy](UI.md#silent-recovery-policy) for all player-facing failures.
