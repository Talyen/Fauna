# Architecture

The [codebase simplification implementation record](SIMPLIFICATION_PLAN.md) documents one journey contract, authoritative formation arrays, shell navigation, typed events and Cloud ownership.

The [journey lifecycle implementation record](archive/GAME_STATE_PLAN.md) documents phase and payload ownership, completed battle receipts, transition contracts and regression evidence.

The [ability resolution plan and implementation record](archive/COMBAT_RESOLUTION_PLAN.md) documents the shared player/enemy executor, approved rule alignment and explicit room scaling.

The [combat reaction architecture plan and implementation record](archive/COMBAT_REACTIONS_PLAN.md) documents typed damage origins, synchronous reaction continuations and the approved immediate cancellation after actor knockout.

`src/game/` owns content, commands, battle rules, seeded RNG, and save validation. It imports only its own modules, Immer, and Zod. It does not access the DOM, React, filesystem, Steam, clocks, or ambient randomness. `scripts/checks/boundaries.mjs` parses source and checks resolved import paths and ambient capability references; CI also runs Knip for unused files, exports and dependencies.

[State schemas](../src/game/state-schema.ts) own the discriminated lifecycle union and [state types](../src/game/types.ts) derive from it. Battle requires active combat; Recruit and Boon choices require their matching completed reward receipt and have no active battle; destinations and terminal results have their own payloads. Every non-draft phase requires a journey summary. [Journey transitions](../src/game/journey.ts) install complete lifecycle payloads within the command transaction. The exhaustive [command phase table](../src/game/command-phases.ts) admits commands before command-specific validation, mutation or RNG consumption. Combat entry points and phase-specific presentation consume narrowed states. Full-roster recruitment banks Collection progress and saves `reward.selectedRecruit` before presentation previews a roster exchange. `confirmRecruit` alone changes the roster or keeps it unchanged; leaving recruitment consumes that saved selection. Local previews never publish game state.

`team` and `reserves` are the authoritative ordered creature arrays. Owned species and deployed IDs are derived from them; saves contain no roster or lineup mirrors. Every phase has expedition state; prepared encounters consume a saved pack under the same eight-battle contract.

`dispatch(state, command)` returns either an accepted immutable state with ordered presentation events or a rejection retaining the original state. Validation occurs before RNG consumption or mutation. Gameplay and progression settle synchronously. Animation is a consumer of results; it cannot pay mana, damage a creature, grant a reward, or unlock content.

`src/application/session.ts` owns the runtime store and serialized save queue. Commands admit the encoded save to the serialized queue before publishing committed state, so synchronous subscribers cannot reorder saves or dispose before an accepted save is admitted. Startup keeps commands unavailable until local loading and bounded cloud reconciliation finish. Load examines primary followed by backups; malformed saves never enter gameplay. All-invalid development candidates silently fall back to a fresh profile; read I/O failures allow in-memory play after an automatic retry or bounded wait. Failed writes retain the live game and retry the latest state in the background. Disposal revokes commands and unsubscribes the close handshake while draining admitted writes.

`src/platform/` defines storage, desktop quit, and optional Steam cloud/achievement capabilities. The browser uses localStorage; desktop uses a sandboxed preload IPC bridge. Steam is optional. Desktop adapters expose display preferences, account-scoped cloud transport and overlay state; gameplay never requires Steam. Cloud reconciliation belongs to the application and native calls run in an owned utility process.

`src/ui/` consumes the session and owns transient targeting, inspection, menu, and input modality. Zustand subscriptions expose application state. Motion respects the user's reduced-motion preference. Standard gamepads and keyboard navigation feed semantic actions and share focus navigation.

The shell [navigation reducer](../src/ui/shell/navigation.ts) owns page and overlay transitions and exposes one active-surface priority for input, rendering, Auto-play and effects. The [focus adapter](../src/ui/shell/focus.ts) keeps DOM references outside navigation and restores semantic menu actions. [Committed event variants](../src/game/types.ts) require the facts their consumers need; [feedback adaptation](../src/ui/battle/combat-feedback-model.ts) owns presentation entries.

Cloud [snapshot validation and hashing](../src/application/cloud-snapshots.ts), [pure reconciliation policy](../src/application/cloud-policy.ts) and [the transport controller](../src/application/cloud.ts) have separate owners. One metadata queue orders snapshot construction, durable metadata writes and publication. Generation checks revoke stale reconciliation; transport never blocks ordinary gameplay saves.

## Domain identity

Species and card definitions use stable authored IDs. A run-specific creature owns three card instances, each carrying its effect level; Legendaries contribute two copies of each definition. Creature IDs persist across deployment and backup moves. Knockout replacements between ordinary creatures retain card-instance slot IDs and zone positions while replacing definitions and owners; swap cards instead remove outgoing slots from all zones and shuffle the incoming kit into the draw pile before subsequent draws. Legendary formation changes reconcile the different kit sizes, retaining reusable slots and shuffling additional slots into Draw. Definition IDs and instance IDs are deliberately independent. The saved lineup stores creature IDs for the next battle and follows committed formation changes; there is no manual lineup editor or free swap of healthy creatures. Multiple copies of a species are supported; swaps, release choices, card ownership and battle hover/focus details address an individual by its ID. The roster species list counts copies rather than enforcing species uniqueness. No individual creature carries progress between runs.

The authoritative aggregate includes permanent species unlocks, win count, keyword XP, talent IDs, and currency; plus the current roster, backup creature state, starting lineup, deployed team/cards, run-wide boons, encounter, phase, and battle. Battle rewards are saved receipts. Banking happens atomically at battle settlement; choosing or skipping a reward never banks them again. Settlement clears active combat and records the completed encounter, outcome and retained earnings in the journey summary. Pending choices contain the corresponding reward offers; they do not retain defeated enemies or card zones. Recruiting and replacing creatures therefore never rewrite completed combat. Combat-only statuses end with combat; roster Health and knockouts persist. Minions are battle-owned records outside the roster; side and summoner identity determine their targeting and lifetime. Enemy Legendaries own separate card zones and Mana. Battle tracks draw, hand, hidden overflow buffer, discard, health/block, enemy targets, turn, and mana. Knockout leaves inert card slots in battle zones. Normal draws skip them and the UI never renders them for knocked-out owners. If all deployed creatures fall, the next draw reserves slots for healthy replacements, allowing recovery without bonus cards. Enemy attacks stop when no deployed target lives; defeat requires all roster members to fall. Pending replacement is derived from the first deployed knockout and living backup, so it needs no saved continuation or UI-owned settlement. After the current command completes, play and End turn are rejected until required replacements finish; only that validated replacement command and gameplay effects can change formation. Both persist the resulting formation for later encounters.

[Rookhaven](content/creatures/rookhaven.md) can add battle-only card copies through the shared draw owner. These initially retain the drawn card’s owner, definition and level, cycle through every ordinary card zone, and use saved unique copy IDs. Ordinary replacements convert outgoing copies to the incoming kit; card-driven swaps shuffle those converted slots into Draw. Legendary formation changes remove copies owned by departing creatures. Copies survive current-format resume and are removed at combat settlement or abandonment. The six-card hand limit is unchanged; the generated deck and overflow share a 256-card bound; adding a permanent kit at the limit replaces the newest generated copies. Save validation distinguishes copies from the required three permanent cards per ordinary deployed creature or six per Legendary.

A linear-congruential RNG is explicit state. Destination offers, shuffles and intent choices consume it; presentation does not. Equal initial seeds and accepted command sequences yield equal results. Rejected commands retain state and RNG.

## Save contract

Development saves are disposable: there are no released player saves to preserve. Do not implement migrations or backward compatibility unless explicitly requested. Obsolete formats are rejected; loading falls back to valid current-format backups or a fresh profile silently. The canonical agent policy is in [AGENTS.md](../AGENTS.md#development-saves).

The current save version is owned by [save-format.json](../src/game/save-format.json), shared by gameplay validation and desktop storage, and included in the packaged application. The phase schemas supply both runtime structure and TypeScript payload types. The current format is validated by Zod and semantic checks for content IDs, ownership, unique card zones, health bounds, lineup completeness, saved encounter packs, and phase/outcome coherence. Only the current format is supported in browser and desktop storage; fixtures track that format. Valid current-format backups remain recoverable.

Battle settlement banks actual retained currency and keyword XP once. Ordinary fights offer recruitment; intermediate bosses offer Legendary recruitment followed by up to three unowned Boons. The shared Victory screen presents committed earnings before a presentation-only Continue opens recruitment; this changes no gameplay revision or save. Recruitment has no Skip action. At a full roster, Recruit banks Collection progress and saves the choice before Confirm commits the displayed team or retains the original roster. Boss Boon choices follow recruitment and retain Skip. There is no gameplay acknowledgement phase or Continue command. An empty Boon pool advances immediately; final victory follows recruitment and defeat goes directly to Journey results. The journey summary retains the outcome, battle count, gains, new unlocks, and last-battle receipt; opening results never grants rewards or saves.

Hands contain at most six cards. Extra draws enter a FIFO buffer, which cannot be played or inspected as a separate zone. Accepted plays refill newly open hand slots from that queue without RNG. End turn discards the visible hand, retains overflow, restores the next player turn’s maximum Mana (four before talent modifiers) and draws four cards after promoting waiting cards. Knockout replacements preserve buffered card slots and update their owner along with other zones. Save validation includes the buffer in zone uniqueness/completeness and rejects a waiting buffer alongside an unfilled hand.

Browser and desktop saves rotate distinct application-validated recoverable checkpoints into two backups before installing the next snapshot. The application supplies the current-format validation predicate with each write; storage adapters import no gameplay implementation and preserve existing backups when no validation policy is supplied. The desktop adapter sends the approved checkpoint bytes through preload; native storage bounds that approval set and matches it against existing slots inside its serialized write lane. Corrupt primaries and repeated writes cannot displace distinct intact recovery checkpoints. Desktop flushes a temporary file, stages each backup, then renames the new save over the primary. A partial backup rotation still leaves the old primary intact. Atomic rename guarantees depend on filesystem behavior; sudden power loss is not equivalent to graceful quit.

Desktop window close and application quit request a renderer flush first. The session pauses new commands, finishes its queue, and retries the latest state once if saving failed before acknowledging close. Main then revokes IPC admission, drains admitted writes, and quits. A persistent save failure is recorded internally and does not prevent closing. Renderer crashes and OS force-kill cannot run this handshake.

## Command resolution and previews

With Auto-end turn enabled (the default), spending the final Mana resolves the enemy turn inside the same command and revision. The play command records its effective preference. Disabling it retains a saveable and resumable player turn at zero Mana; normal victory/defeat settlement remains immediate. Preview resolution is independent of this setting. Victory takes precedence over automatic turn advancement. Card previews run the same card-effect resolution without settling battle rewards, advancing the enemy turn, or publishing/saving the preview state. This retains the final enemy health forecast even when committing the card will advance directly to destinations.

## Discovery and diagnostics

Permanent discovery stores encountered species and recruited copies. All species are available to encounter and recruit. Collection and later starter drafts use only recruited species. First-journey onboarding samples three offers from the authored eligible pool and starts with one chosen creature, collecting it when the final Recruit starts the journey. Later journeys normally save three rounds of three offers and require three picks; choosing a Legendary as the first pick completes the draft alone and later rounds offer only ordinary creatures. Accepted battle entry discovers the exact enemy group, and accepted recruitment increments its permanent copy count, capped at six. The first copy collects the species at zero stars; duplicates add one star each, up to five. The committed onboarding starter supplies one initial copy; later starter drafts grant no copies. Releasing journey creatures never removes permanent copies. Each species owns six passive tier slots in content. Authored tiers replace the full passive and can compose card bonuses, battle-start effects and reactive effects. All six tiers are required and must have distinct gameplay effects; catalog validation rejects missing tiers and repeated effect sets even when their wording or ordering differs. Combat, previews and inspection resolve the same player tier, while enemies retain base effects. Only accepted recruitment and the first onboarding starter collect species. Collection uses the shared creature inspector for the permanent active trait, progress stars and three base abilities with hover/focus rules, independently of journey card upgrades and battle modifiers. Collection is accessible through battle Pause and returns to unchanged combat. Collection browsing and out-of-battle inspection consume no RNG, grant no discovery and write no save. Loss, return home and new journeys retain knowledge. Save validation rejects duplicate or unknown discovery records, recruitment without an encounter, ineligible starter offers, incomplete offers and invalid selections. Starter offers persist across reloads and rejected commands preserve RNG. Ordinary enemy groups grow from one to two to three across the first three battles and stay at three thereafter; bosses begin with one Legendary. No historical discovery is inferred for obsolete saves.

`src/application/diagnostics.ts` owns a bounded local collector exposed by the session. Its platform port owns persistence, separate from the game save. Entries contain selected revision/phase fields rather than arbitrary game objects. No player-facing report or clipboard export is exposed. Sink failures and recursive logging cannot affect commands or saves. Session disposal revokes collection. `committedCommand` is transient session presentation metadata and never enters the saved aggregate; loading a checkpoint does not manufacture a new committed action or replay audio.

## Combat and destination health

`src/game/combat/abilities.ts` owns the single synchronous ability executor for player cards, previews and enemies. It resolves repeats, targets, primary effects, recipient extras and global extras within the engine's Immer transaction. Exhaustive switches require explicit execution and support decisions for new effect kinds. The engine retains command validation, Mana, card zones, accepted-play counters, XP, turn scheduling and final settlement. Application publication and saves remain outside gameplay.

`src/game/combat/ability-values.ts` shares magnitude policy between execution and displayed rules. Both sides start with authored ability values and the same intrinsic passive calculation. Enemies store explicit room power (1 + room index / 10); ability damage, healing and Block scale once, including extras. Chances, effect counts, resource grants and passive tiers do not scale. Enemy Health uses the same depth curve. Save validation requires the exact power and Health for the saved encounter; obsolete development saves are rejected without migration.

`src/game/engine.ts` retains the command transaction, validation and command routing. [Journey transitions](../src/game/journey.ts) own encounter preparation, battle setup and reward settlement; [team operations](../src/game/team.ts) own card ownership, lineup preparation and swaps; [battle turns](../src/game/combat/turns.ts) own enemy action windows and the next player turn. These mutate only the admitted command draft and keep RNG and event order synchronous.

`src/game/combat/index.ts` exposes shared combat entry points. [Combat policy](../src/game/combat/policy.ts) owns typed packet origins and reaction eligibility; [combat resolution](../src/game/combat/resolution.ts) owns synchronous, depth-first reaction continuations for damage, healing, protection, statuses, Leech and control. [Damage](../src/game/combat/damage.ts), [protection and healing](../src/game/combat/protection.ts), [statuses](../src/game/combat/statuses.ts) and [action lifecycle](../src/game/combat/lifecycle.ts) handlers yield [typed operation requests](../src/game/combat/operations.ts), with no runtime imports between handlers or back into the scheduler. The scheduler registry must satisfy the operation contract. Generator frames yield typed child operations to a local stack; children finish before their parent resumes, without recursively entering mutation handlers. [Combat state helpers](../src/game/combat/state.ts) own atomic mutations and read-only queries. Armor removal records a transient, once-delivered depletion receipt at the positive-to-zero transition; later regrant and depletion produce a new receipt. No stack, receipt or continuation enters saves or published state. Retaliation knocking out the acting creature stops its remaining hits, extra effects and repeats; Death's Door at 1 Health allows continuation. Existing committed effects remain applied. Seeded Dodge and 5% base Critical chance retain their packet policies. Both sides use half maximum Health for Stun/Freeze. Player-only Death's Door, talents, Boons, card upgrades and collected passive ranks are explicit ownership exceptions. Enemies use base passive tiers and have no automatic round healing. The command resolver delegates turn sequencing and final settlement to these gameplay helpers inside the same transaction; enemies knocked out by their start-of-turn status damage cannot act. Ordinary enemies select a supported species ability without immediately repeating the last choice. The exhaustive enemy adapter omits hand/Mana extras and excludes unsupported resource-only abilities; draw-plus-self-heal converts to its healing effect. Enemy Legendaries instead use their own deck, hand and Mana through [Legendary combat](../src/game/combat/legendary.ts); Memento’s draw and Pearl generation are explicitly supported. Enemy target choices are AI policy, not a separate effect implementation. Selection happens at the action window, never during inspection, and next intentions remain hidden.

Health and knockouts persist through victories, rewards, formation changes and destination entry. Battle setup resets combat effects without restoring Health. Campfire appears beside destination choices whenever any roster creature, including a backup or knockout, is missing at least 30% of maximum Health. Rest restores 30% maximum Health to the whole roster, capped at full Health, and returns to the same combat offers without advancing the encounter or changing RNG. The most recently visited room type is suppressed on return, so Campfire cannot be repeated immediately. Visiting enters a saved Campfire phase. Rest awards no Gold or XP. Eligibility and displayed recovery share the gameplay helpers in `src/game/destinations.ts`.

Draw and discard surfaces use blank portrait art and the existing modal owner. During battle, card rules remain on hover/focus without nested inspection. Pile viewers sort by definition and instance identity, never draw order. Browsing does not publish gameplay, consume RNG or save.

## Automated and development combat

The pure application battle policy scores only visible cards and creatures, using stable identity tie breaks and no gameplay RNG or hidden intentions. Headless heuristic runs and player Auto-play share it. Potential finishing primary hits outrank routine healing and Minion kills; ordinary damage, Block depletion and Armor erosion have value, and Purge precedes attacks against visible defenses. These are heuristic estimates rather than complete combat forecasts. Ranked choices expose a decision reason for automation journals. The UI scheduler admits at most one command per 700 ms, pauses while obscured or unfocused, and cancels pending callbacks on manual takeover, completion, navigation home or disposal. It never makes reward or progression choices. Session disposal makes readiness unavailable before draining admitted saves.

Development victory uses an explicit session capability supplied only by development startup. Ordinary dispatch rejects it. It marks enemies defeated and reuses ordinary settlement, events and saving, preserving roster Health and banking actual earned XP. Packaged desktop startup ignores development URLs.

Results return directly home; reopening completed results grants no additional progress.

Talent categories are consolidated independently of combat damage identities. The current format stores Boon IDs, first-Burn consumption, periodic status attribution, pending creature-owned talent rewards, remaining control windows, and already-banked talent Gold. Old development saves, including Forge state and relic fields, are rejected. No capability or local display preference is restored from progression.

## Support visits and spending

Recruit and Boon Merchant destinations each roll independently at a 25% chance when preparing destinations, with eligibility checked separately. Recruit requires fewer than five roster creatures and offers one uniformly selected ordinary species from the catalog; activation recruits directly, consumes the offer and updates collection progression without advancing the encounter or RNG. The route saves that offer and the last visited room type; returning options suppress the last visited type, while Combat or Boss remains available for progression. Boon Merchant is visible and enterable only when at least one stocked item is affordable. Campfire preserves saved offers; completing a Boon Merchant visit prepares fresh destinations at the same battle ordinal, excluding another Merchant. Boon Merchant stock contains up to three unowned Boons, each with an independently rolled integer price of 20–40 Gold inclusive, or 13–33 with Merchant’s Favor when stock is prepared, with one purchase per visit. Gold is the existing permanent currency. Entering commits a visit; buying atomically grants the Boon and opens its saved reward screen. Leaving, Back or reward Continue completes the room and prepares the next destinations; beginning a battle forfeits an unvisited Merchant. Inspection is read-only. Commands address visit/slot identities and validate before mutation; reload cannot refresh stock or repeat purchases. Merchant state remains valid during a Campfire visit.

Journey currency measures gross retained earnings, independently of the remaining wallet. Boss rewards contain up to three eligible unowned Boons and skip only an empty pool. Support state, stock, price bounds, receipts and phases are validated together in the current save format; obsolete development saves are rejected.

## Cloud reconciliation and device preferences

`src/application/cloud.ts` validates current gameplay payloads and hashed envelopes, compares causal ancestry, and owns automatic conflict resolution. It never merges progression fields. Each device writes two alternating remote slots; another device's slots are read-only. Unknown ancestry creates competing heads; prefer the intact local head, otherwise choose by stable snapshot ID, and preserve alternatives before recording all heads as ancestors. Replacements preserve competing snapshots locally before installation through the serialized save lane. Snapshot lineage is bounded to 64 ancestors and remote inventory to 32 device streams / 64 files, at most 1 MiB each. Invalid or oversized files pause upload; they are not deleted.

Local saves remain authoritative offline. Failed sync retries in the background without replacing the active journey, preserving remote alternatives before recording their ancestry. Cloud metadata is durably written after the local gameplay save and before upload; transport cannot hold the local save queue. Cloud failures remain internal while local play is safe; persistent local save failures receive the minimal notice defined in the UI recovery policy. Startup reconciles before command admission and automatically continues locally after failure or a five-second wait. Late reads cannot replace a session after offline takeover. Shutdown drains admitted local writes and allows at most two seconds for uploads. A utility process contains blocking native transport and is terminated on owned app shutdown. Failed native sends retire their request and timeout together. Steam teardown has one shared completion, revokes overlay callbacks immediately and continues independent cleanup and metadata draining if native cleanup throws.

`desktop/steam.cjs` pins an optional Steam account, isolates its local profile from standalone progress, and automatically adopts valid standalone progress for a new Steam profile while preserving the original. `desktop/steam-config.json` holds Fauna's own App ID; its default null disables real Steam. Browser, smoke, preview and performance profiles never access live Steam. Account changes reject transport and require restart. Without a Steam client, ordinary launch continues the last locally used Steam profile with sync unavailable; isolated automation ignores that pointer. A newly identified account always selects its own directory, and the standalone original remains separate. Overlay activation synchronously revokes commands, cancels targeting/Auto-play and opens the existing pause menu; closing the overlay does not resume automatically.

`desktop/display.cjs` owns Windowed/Fullscreen and reachable window bounds, stored separately from progression and Cloud. Renderer settings use the typed authorized preload capability; automation has fixed isolated geometry. Native transitions and monitor removal never change artwork dimensions. The packaged renderer uses a restricted `fauna://app/` protocol rooted at `dist/`, rejecting foreign authorities, traversal, symlink escapes and writes. Native permission requests and checks deny access. Production CSP denies network connections; development alone permits loopback HMR. File-protocol privileges are disabled.

Renderer crashes retain local platform facts and local native crash dumps without uploads. Recovery drains admitted local writes before reloading, with at most two reloads per app process and no recovery after close begins. The renderer resumes through ordinary validated save loading.

After-pack fuses and browser snapshots are checked on the actual Windows artifact before the renderer-only packaged smoke; Node inspection is disabled.

Save loading tries intact current-format backups without announcing recovery. All-invalid development saves fall back to a fresh playable profile. Read access failure is retried once, then allows in-memory play; failed writes retry every five seconds with the newest committed state and stop on disposal. A write following read failure must first regain read access so unknown data is not blindly rotated. See the [recovery policy](UI.md#recovery-and-persistent-failures) for all player-facing failures.
